## Configuration and manual checkout

1. Complete README local setup, including pnpm db:provision-payments before applying Phase 3 migrations. Seed unpaid synthetic orders with line items.
2. In the PayPal Developer Dashboard, create/select a Sandbox Business seller and a separate Sandbox Personal buyer. Create/select the seller's Sandbox REST app and copy its client ID/secret. Retrieve the seller's merchant ID. Keep the buyer login in the PayPal approval window, never in the repository.
3. Expose the local API through a publicly reachable HTTPS development tunnel on port 443. Register https://YOUR-TUNNEL/api/v1/webhooks/paypal/demo-sandbox on that same Sandbox app and select the event types above. Copy the resulting webhook ID. Tunnel provisioning is manual and was not performed here.
4. Set ignored .env values: PAYPAL_ENABLED=true, PAYPAL_ENVIRONMENT=sandbox, PAYPAL_CLIENT_ID, PAYPAL_CLIENT_SECRET, PAYPAL_MERCHANT_ID, PAYPAL_WEBHOOK_ID, PAYPAL_ACCOUNT_KEY=demo-sandbox, PAYPAL_TENANT_ID (the local merchant UUID) and WEBHOOK_PAYLOAD_ENCRYPTION_KEY (32 random bytes encoded as 64 hex characters). Use the provisioned WORKER_DATABASE_URL. The default development merchant UUID is 10000000-0000-4000-8000-000000000001.
5. Run pnpm paypal:configure to bind that seller to the tenant and dedicated worker role. This writes configuration metadata, not credentials, and makes no provider call. Never bind one seller's funds to unrelated tenants.
6. Restart pnpm dev so both API and worker load the settings. Open http://localhost:5173/checkout. Sign in as customer@resolveai.test with the generated local DEV_SEED_PASSWORD. Select an unpaid owned order, confirm its USD amount and select Pay with PayPal Sandbox.
7. Approve using the separate Personal Sandbox account. The API schedules capture; the worker verifies seller, order association, gross amount/currency and completed capture before committing Order.PAID. The UI displays the verified capture ID and timestamp.
8. Refresh/repeat an identical request to confirm the same operation/capture. Inspect the merchant's Sandbox transaction record and actual webhook delivery. A callback, popup closure, HTTP202 or event name is not proof of payment.

An optional terminal-driven real smoke is pnpm test:sandbox, with RUN_PAYPAL_SANDBOX=true and SANDBOX_ORDER_ID set to an unpaid customer order. It authenticates through ResolveAI, creates the order, pauses for manual buyer approval, requests server capture and records only a scrubbed provider-confirmed result in ignored .local/sandbox-last-run.json. It is excluded from CI and pnpm check. Missing credentials/opt-in cause an explicit error, not a fabricated or skipped-success result.

## Durable workflow and safety

The API preserves /api/v1 naming. Authenticated customer writes require exact ownership, Origin, CSRF, Idempotency-Key and If-Match. Item totals use quantity*unitMinor + line-total taxMinor + line-total shippingMinor; the sum must equal stored order amount. Currency is USD. After intent creation, totals/customer association and outbound payload/key/account are frozen.

CREATE and CAPTURE are separate existing CheckoutOperation rows, with one logical row per kind/order. HTTP replay is actor/route/key/body-scoped; database uniqueness survives cache expiration. Worker claims have 90-second leases and token-fenced commits. No transaction spans OAuth, PayPal, Redis or signature-verification calls. Returned order IDs are durably observed before follow-up GET verification; they are not presented as verified checkout until the create operation completes.

Outbox dispatch leases due events, enqueues IDs, and acknowledges the database only after queue acknowledgement. Duplicate delivery is expected. A database sweeper independently rediscovers due/nonterminal operations and both unverified and verified-but-unfinished receipts, including after queue loss or worker restart.

A capture timeout remains UNKNOWN/RECONCILIATION_REQUIRED. Known IDs are reconciled via GET; approved-but-uncaptured orders retry only the identical request/key within the deadline. After the mutation deadline, authoritative reads may continue, but no new key is generated. An unknown create without a recoverable provider ID eventually freezes for manual investigation. This release deliberately does not mint replacement provider orders after failure/uncertainty; operators must investigate before providing another payable order.

Capture rows contain verified completed payments only. Pending capture IDs/statuses live on operations; they cannot mark orders paid. Successful persistence atomically inserts the unique capture, completes the operation, marks the order paid and appends audit. Currency, full gross, seller and authenticated order/capture relationship must match. Provider mismatches freeze for review. Local leases fence database writes, not already-sent external requests; provider keys and the single-provider-order model remain necessary.

## Webhooks and tenant access

The public endpoint accepts bounded original JSON and required PayPal headers, then invokes a narrow fixed-search-path database receipt function. It resolves only an enabled configured account key, encrypts original bytes with AES-256-GCM, deduplicates delivery fingerprints, and creates inbox/receipt/outbox records atomically. It has no generic cross-tenant table capability. Receipt acknowledgment is not verification acceptance.

Worker role assignment is stored on PaymentAccount. Only explicitly assigned enabled accounts are discoverable. Tenant transactions establish app.merchant_id; FORCE RLS checks both that context and account assignment. Workers have no access to authentication, cases/proposals or RefundOperation, no owner/superuser/BYPASSRLS privileges, no role membership and no schema creation. Public ingress is the only SECURITY DEFINER addition and its EXECUTE privilege is narrowly granted.

Verification uses original JSON formatting in webhook_event; no certificate URL is downloaded. Invalid receipts cannot become payment facts or permanently poison the event identity; later valid deliveries are separately verified. Verified events still require authenticated resource GET and association checks. Duplicate/older events cannot downgrade completed payments. A provider-observed reversal or changed settlement freezes the capture and marks review required; no refund or dispute action executes.

Remaining operational work before live use includes account onboarding, distributed token/cache choices, monitoring/alerting, receipt retention/cleanup, production key rotation/encryption, real SDK/browser/account verification, provider-specific failure classification and broader operational review. Internal complaints, refunds, AI and formal disputes remain separate later phases.

SDK popup sessions explicitly use commit:true. Preserve the callback-driven Orders flow; no redirect experience was added. PAYPAL_WEBHOOK_ID is the alphanumeric webhook identifier from PayPal, never the webhook URL. Sanitized SDK diagnostics are available in sessionStorage under resolveai.paypal.lastError.

## Phase 6 refund contracts (mock verification only)

The typed client implements POST /v2/payments/captures/{capture_id}/refund and GET /v2/payments/refunds/{refund_id}, using server-selected amounts and a durable PayPal-Request-Id. Capture/order GET verification confirms the original account/order relationship; refund amount/currency/invoice/up-capture link must match the immutable local intent. See [refund API](https://developer.paypal.com/api/payments/v2/captures-refund), [refund lookup](https://developer.paypal.com/api/payments/v2/refunds-get) and [request idempotency](https://developer.paypal.com/api/rest/requests/). No indefinite retention or search-by-request-ID capability is assumed. This implementation deliberately permits at most one uncertain dispatch per intent, preserving reservations and using GET/webhook/manual reconciliation rather than blind replay. Real refund calls remain disabled and were not tested.

The earlier Phase 3 worker-table access description is historical: Phase 6 adds only scoped settlement/refund records and selected Case/Proposal columns, without private descriptions/terms or authentication access. A separate credential-free mock worker provides the synthetic demo. See PHASE-6-REPORT.md.
